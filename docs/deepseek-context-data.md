# DeepSeek 上下文实测：为什么是 300 / 500 / 650 / 800K

> 数据日期：2026-11-26  
> 环境：本机 OpenCode 2.4.1，主模型 `deepseek/deepseek-flash`（DeepSeek V4.1 Flash 1017，1M 窗口）  
> 样本：**18,471 条** DeepSeek assistant 消息；**67 个** DeepSeek 长会话（总消息 ≥50、DS 占比 ≥80%）；**22 个**会话有完整 part 组成数据  
> 结论边界：**只对 DeepSeek 这类“1M 窗口 + 超低缓存价”的主模型特调；其他模型仅作参考，默认仍用 50%/60% 窗口。**  
> 复现：`python3 scripts/measure-context.py`（只读 DB，不输出标题/正文/密钥）

---

## TL;DR

1. **上下文约 2/3 是工具输出，约 1/3 是思维链，正文不到 1%。**
2. **上下文 ÷ 累计思维链：中位数 3.46×**（p25 3.09，p75 4.79）。
3. **0–800K 没有观察到质量代理指标恶化**：工具错误率 0.0–0.7%，助手错误 0.0–0.2%，重试 0。
4. **上升的是成本和耗时**：500–600K 时单条消息成本约为 0–50K 的 3.6×，耗时约 2.6×；800K+ 成本约 9×。
5. **会话自然结束位置**：p50 247K，p75 480K，p90 710K，p95 787K。
6. 因此 DS 推荐区间：**300K 软提醒 → 500K 交接 → 650K 硬换 → 800K 不建议常驻**。
7. 最初设想的 **1×/1.5× 思维链不是质量阈值**；按 67 个会话回放，它会在会话 25%/38% 处触发（上下文约 100K/150K），等于每 100–150K 换一次窗，质量上没必要，只是成本激进。
8. **新会话不是重新付满 10K**：首请求 5.4K（p50）/10K（p90），98% 命中共享缓存；未命中仅 1.2K/5K。加 handoff/任务数据 1–5K 后，首轮约 **0.003–0.018 元**（热/冷），典型 0.01 元上下——约 1–3 轮旧上下文成本。

## 1. 样本与方法

### 数据源

- `~/.local/share/opencode/opencode.db`（只读）
- `session_message` 中 `type='assistant'` 的消息
- 仅统计 `model.providerID = 'deepseek'`

### 口径

| 指标 | 定义 |
|---|---|
| 上下文 | `tokens.input + tokens.cache.read + tokens.cache.write` |
| 思维链 | `tokens.reasoning` |
| 工具错误 | assistant `content` 中 `type='tool'` 且 `state.status='error'` |
| 助手错误 | 消息 `error` 字段非空 |
| 重试 | 消息 `retry` 字段非空 |
| 耗时 | `time.completed - time.created` |
| 长会话 | 总会话消息 ≥50，且 DeepSeek 占比 ≥80% |
| 组成统计 | `session_part` 中 tool / reasoning / text 的字节占比 |

### 分层

- 18,471 条 DS 消息用于分桶。
- 67 个 DS 长会话用于会话内前后半段对比和最终上下文分布。
- 22 个有完整 part 的会话用于字节组成。

## 2. 上下文组成

### 按字节（22 个会话）

| 组成 | p25 | 中位数 | p75 |
|---|---:|---:|---:|
| 工具输出 `tool` | 62.5% | **66.2%** | 76.8% |
| 思维链 `reasoning` | 22.6% | **33.0%** | 36.6% |
| 助手正文 `text` | 0.6% | **0.8%** | 1.0% |

### 按 token（67 个会话）

| 指标 | p25 | 中位数 | p75 |
|---|---:|---:|---:|
| 上下文 / 思维链 | 3.09× | **3.46×** | 4.79× |
| 思维链占上下文（低膨胀→高膨胀） | 32.4% | **28.9%** | 20.9% |

> 注：`C/R` 越小，思维链占比越高。表中“32.4%”对应 C/R 的 p25，“20.9%”对应 p75，避免把分位方向看反。

**解读**：工具输出是唯一的大头；RAG/文档正文在代码会话里不到 1%。  
所以“省上下文”不是少读文档，而是**把工具结果先筛后回**。

### 要到 1.5× 需要砍多少

- 目标思维链占比 66.7%
- 当前约 28.9%，工具+正文约 71.1%
- 需砍掉约 37.8 个百分点 → **工具输出约砍一半**

## 6. 成本与延迟

按上表取几个关键点（`$/msg` 为 OpenCode 记录的单条消息成本，含缓存/新 token/输出）：

| 上下文 | 相对成本 | 单条耗时 |
|---|---:|---:|
| 0–50K | 1.0× | 2.6s |
| 100–150K | 1.4× | 4.1s |
| 300–400K | 2.4× | 5.4s |
| 500–600K | 3.6× | 6.9s |
| 800K+ | 9.1× | 6.9s |

DS 官方价（元/百万 token）：缓存命中 0.02、输入 1、输出 4；高峰翻倍。  
因为缓存命中极便宜，**质量没坏时，成本本身不是立刻换窗的理由**；真正推动换窗的是延迟、任务边界和连续性。

### 新会话注入成本（冷启动）

新会话第一请求要注入 system prompt、工具定义、skills 描述、handoff 与任务数据。  
本机 100 个 DS 会话的首请求实测：

| 指标 | p25 | p50 | p75 | p90 |
|---|---:|---:|---:|---:|
| 首请求 prompt tokens | 5,255 | **5,418** | 7,442 | **10,053** |
| 其中缓存命中 | 2,688 | 4,224 | 5,760 | 7,296 |
| 未命中 input | 256 | **1,214** | 3,308 | **5,013** |
| 输出 | 98 | 128 | 159 | 239 |
| 实际首轮成本（$） | 0.00021 | 0.00033 | 0.00065 | 0.00099 |
| 冷启动成本（$，无缓存） | 0.00087 | 0.00095 | 0.00124 | 0.00175 |

**98% 的首请求已有缓存命中**：system/tools/skills 是跨会话共享前缀，实际只付未命中的 1–5K。

加上 handoff（1–2K）和任务数据（1–5K），按 7.2 汇率折算：

| 额外数据 | prompt 约 | 热启动（元）p50/p90 | 冷启动（元）p50/p90 |
|---:|---:|---:|---:|
| +0K | 5–10K | 0.002 / 0.007 | 0.007 / 0.013 |
| +1K | 6–11K | 0.003 / 0.008 | 0.008 / 0.014 |
| +3K | 8–13K | 0.006 / 0.010 | 0.010 / 0.016 |
| +5K | 10–15K | 0.008 / 0.013 | 0.012 / 0.018 |
| +8K | 13–18K | 0.011 / 0.016 | 0.016 / 0.021 |

对比旧上下文：500K 每轮缓存读约 **0.011 元**，650K 约 **0.014 元**。  
所以一次 handoff + 新会话首轮（含 1–5K 数据）通常 **0.01–0.03 元**，约 **1–3 轮**旧上下文成本；换窗的主要成本是连续性，不是钱。

> 注意：改 `AGENTS.md`、skills、工具定义会让共享前缀失效，落到“冷启动”一列。  
> 如果 handoff 由主模型写 1–2K 输出，再加约 0.006–0.012 元；本插件的 `handoff` 是确定性模板，不额外调模型。

### 动态预测公式与校验

`ctx_forecast` 用当前会话数据做确定性计算：

```text
C = input + cache.read + cache.write
R = Σ reasoning
G25/G50/G75 = 最近 10 次上下文增量的分位
N(t) = (t - C) / G          # 到目标上下文 t 的轮次
P_next = P_base + H_doc + D_task
U_next = U_base + H_doc + D_task
Cost_next = (U_next×p_in + Cache_base×p_cache + O_base×p_out) / 1e6
Payback = (H_doc×p_out + Cost_next) / (C×p_cache)
```

- `P_base/U_base/Cache_base/O_base` 取 100 个 DS 首请求的 p50/p90。
- `p_in=1`、`p_cache=0.02`、`p_out=4`（元/百万，DS 官方）。
- `G` 用最近 10 次增量，输出 `fast/mid/slow` 三档，而不是单点。

历史校验（67 个 DS 长会话）：

| 预测项 | 误差 |
|---|---|
| 首请求 prompt | MAE **435 tokens** / MAPE **8.5%**；p25–p90 覆盖 66% |
| 到 300K 的轮次 | MAE **23 轮**，p90 99 轮，MAPE 37.3%，区间覆盖 50.2% |
| 到 500K 的轮次 | MAE **41 轮**，p90 192 轮，MAPE 35.7%，区间覆盖 50.1% |
| 到 650K 的轮次 | MAE **55 轮**，p90 240 轮，MAPE 33.1%，区间覆盖 50.9% |

**结论**：

- “下一次重开首轮注入”可以当预测用（误差 <10%）。
- “还剩几轮”只能当粗估：上下文增长是突发的工具输出，不是线性的；给出 `fast/mid/slow` 区间，不承诺单点。
- `explain:true` 可选调用 Qwen3.8 Flash，把 JSON 解释成 3 行；没有 DashScope key 时只回数学结果。

### 偏差过大时的校准闭环

`ctx_forecast` 会写 `~/.local/share/opencode/ds-saver/last-forecast.json`。  
实际偏差 > 50%（上下文 / 下次注入 / 轮次任一）时，调用 `ctx_calibrate`：

```text
ctx_calibrate(actual_turns=20, actual_context=620000, actual_next_prompt=11200, explain=true)
```

- 确定性重算：`observed_G = (C_actual - C_forecast)/turns`，`multiplier = clamp(observed_G/old_G, 0.5, 2.0)`，`new_G = old_G × multiplier`。
- 写 `calibration/latest.json` + `calibration-*.md` 交接文档。
- Qwen3.8 Flash 只写 5 行交接说明，不参与算数。
- 下一次 `ctx_forecast` 自动读取 `latest.json`。

完整协议见 `docs/calibration-protocol.md`。

## 7. 最优区间（DS 专用）

| 区间 | 上下文 | 动作 | 依据 |
|---|---:|---|---|
| 绿 | **0–300K** | 正常 | 约 57% 会话在 300K 以下结束；成本/延迟最低 |
| 黄 | **300–500K** | `misc` 筛工具输出，准备 handoff | 约 43% 会话越过 300K；成本 2–3× |
| 橙 | **500–650K** | 在自然断点 handoff 换窗 | p75 约 480K；成本 3–4×，耗时 ~7s |
| 红 | **650–800K** | 必须换窗 | p90 710K；成本 4–9× |
| 禁 | **>800K** | 不建议常驻 | 仅 4.5% 会话；接近 891K 压缩线 |

**50% 提醒 = 524K**：落在橙区入口，适合作为“绝对提醒上限”。  
**60% = 629K**：落在红区边缘，适合作为“硬换线”。  
数据建议把**第一次软提醒提前到 300K**，否则前 43% 的长会话没有缓冲。

## 8. 思维链比值怎么用

`C/R`（上下文 ÷ 累计思维链）中位数 3.46×，但它**不是质量指标**，而是“工具膨胀度”：

| C/R | 思维链占比 | 含义 | 动作 |
|---:|---:|---|---|
| > 5 | < 20% | 工具输出严重膨胀 | 先 `misc` 筛，再考虑 handoff |
| 3–5 | 20–33% | DS 常态 | 按 300/500/650K 正常走 |
| < 2 | > 50% | 思考很重、上下文很紧 | 可以放到 650K 再换 |

**不要用 1×/1.5× 直接当阈值**：  
按 67 个 DS 会话回放，`1×/1.5×` 会在会话 25%/38% 处触发（上下文约 100K/150K），等于每 100–150K 换一次窗；质量上没有必要，只是成本激进。

## 10. 局限

1. **没有任务成功率标签**：质量结论只基于工具错误、助手错误、重试、输出长度、耗时等代理指标。
2. **单机单用户样本**：67 个长会话、18,471 条消息，不能代表所有 DS 使用方式。
3. **任务类型混杂**：长会话可能本身更难；会话内前后半段对比只能部分控制。
4. **模型版本固定**：DeepSeek V4.1 Flash 1017；换版本需要重新测量。
5. **成本是 OpenCode 记录值**：受缓存命中、模型路由、时段价格影响，适合看相对趋势，不适合当账单。
6. **结论只对 DS 特调**：其他模型默认 50%/60% 窗口；如要套用，需要先确认缓存价差和窗口。

树状文档 + RAG 检索 + 低价 agent 代工 + 数据驱动的换窗策略。

### 问题

长代码会话里，上下文很快被工具输出塞满；传统 compaction 是“有损摘要”，还会打断任务。  
DeepSeek 的缓存很便宜，但缓存不是免费，延迟也会随上下文上升。

### 它做什么

- **`misc`**：把工具输出/日志/文档交给低价官方模型筛选，只回短结论。默认 混元 Hy4 Flash → MiMo V2.6 Flash → Qwen3.8 Flash。
- **`tree`**（规划）：上层文档树只返回目录 + 一行摘要，不塞全文。
- **`rag`**（规划）：下层检索 top-k + 引用；当前事实仍以现状页为准。
- **`ctx_status`**：只读查看上下文、缓存命中、成本、`C/R` 诊断。
- **`ctx_forecast`**：预测下一次重开首轮注入、当前任务截至 token、剩余轮次区间与 handoff 回本。
- **`ctx_calibrate`**：预测偏差 > 阈值时，重算 growth/base，写校准交接文档；Qwen3.8 Flash 可选。
- **`ctx_report`**：采集一条匿名指标到本地 `metrics.jsonl`，用于真实数据反馈与阈值校准。
- **`handoff`**：到 500K 左右生成交接文档，开新窗口；不删历史、不做有损摘要。

### 为什么是 DeepSeek 专用

基于本机 18,471 条 DS 消息、67 个长会话：

- 上下文约 **66% 是工具输出**、33% 是思维链、正文不到 1%；
- **0–800K 没有观察到质量代理指标恶化**；
- 成本/耗时随上下文上升，p75 会话在 **480K** 结束；
- 新会话首请求 5.4K/10K，98% 命中共享缓存，换窗首轮约 **0.01–0.03 元**；
- 所以采用 **300K 软提醒 / 500K 交接 / 650K 硬换 / 800K 不建议常驻**。

其他主模型只使用 50%/60% 窗口参考值，不套用 DS 的 300/500/650K。

```sh
./install.sh
```

### 安全

- 拒绝读取 `03-密钥`、`.env*`、`auth.json`、私钥、插件配置等敏感路径。
- 材料命中私钥/`sk-`/`tp-`/`api_key=` 等模式时中止，不发给外部 API。
- `misc` 的 agent 模式只读文件，不跑 shell、不改文件。
